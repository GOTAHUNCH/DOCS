# Platform Architecture

Hunch is built in three layers. The **experience layer** is what users touch. The **routing layer** turns a swipe into an order on the right venue. The **venue layer** is where markets live, trades fill and outcomes resolve — Polymarket today, more venues over time.

## Three Layers

| Layer | What it does | Technology |
| --- | --- | --- |
| **Experience** | Swipe feed, social graph, points, leaderboards, portfolio | React Native app, Hunch API |
| **Routing** | One adapter per venue; picks the venue for each market and user; signs and relays orders; tracks positions | Hunch API + worker (TypeScript) |
| **Venues** | Order books, liquidity, settlement, resolution | Polymarket (live), Kalshi (planned), Hunch Native (planned) |

## Venues

| Venue | Status | What it is | How Hunch earns | Settles on |
| --- | --- | --- | --- | --- |
| **Polymarket** | Live at launch | Builder Program — Hunch orders fill on Polymarket's order book | 1% builder fee on taker volume | Polygon, pUSD |
| **Kalshi** | Planned | Kalshi Builder Codes — regulated, US-listed event contracts | Up to 30% fee share plus Hunch fee | Kalshi (USD) or Solana via DFlow |
| **Hunch Native** | Planned | User- and creator-made markets on Hunch's own contracts | Platform fee, shared with creators | Robinhood Chain |

Details of each venue are on the [Venues & Settlement](/whitepaper/venues) page. The routing layer treats every venue identically — catalogue, prices, account, quote, order, positions, resolution — so adding a venue is a new adapter, not a new app.

## System Components

| Component | Technology | Purpose |
| --- | --- | --- |
| Mobile app | React Native | iOS, Android and web from one codebase |
| Authentication & keys | Privy | Social login, embedded wallet that owns the user's venue accounts |
| Trading accounts | Polymarket Deposit Wallet + session key | Holds the user's pUSD and positions; session key trades without prompts |
| Gas & relaying | Polymarket Relayer | Gasless wallet deployment, approvals, trades and redemptions |
| API | TypeScript on Google Cloud Run | Auth, feed, trade routing, points, admin |
| Worker | TypeScript on Cloud Run Jobs | Market catalogue sync, live prices, resolution, points accrual |
| Database | Supabase (PostgreSQL) | Users, feed state, trade mirror, points ledger |
| Secrets | Google Secret Manager + Cloud KMS | Builder credentials; per-user session keys encrypted at rest |
| Market data | Polymarket Gamma, CLOB, Data API, real-time websocket | Catalogue, order books, positions, prices |
| Future token | $HUNCH on Robinhood Chain | Rewards, fee rebates, native-market collateral, governance |

## Data Flow

<Steps>
  <Step title="Catalogue">
    The worker pulls open markets from each venue, categorises them and streams live prices into the database
  </Step>
  <Step title="Feed">
    The API builds a personalised deck: unseen markets first, then skipped, then already-traded, filtered by category and time to close
  </Step>
  <Step title="Swipe">
    The app sends one request. The API quotes the venue, signs a marketable order with the user's session key, attaches the builder code and relays it
  </Step>
  <Step title="Position">
    The fill is mirrored locally, points are credited, and the user's portfolio updates from the venue's data API
  </Step>
  <Step title="Resolution">
    The worker watches the venue for resolution and redeems winning positions gaslessly
  </Step>
</Steps>

## Scalability

The architecture is designed to scale to millions of users:

| Component | Capability |
| --- | --- |
| API | Stateless containers, autoscaled behind a load balancer |
| Worker | Scheduled jobs with database locks; venues polled in bulk, prices streamed |
| Database | Supabase handles 10,000+ concurrent connections |
| Venues | Polymarket processes billions in volume; Hunch adds load only at the edge |
| Caching | Redis layer planned for high-frequency data |

<Info>
  Current infrastructure supports ~100K monthly active users. Scale upgrades are straightforward and budgeted in growth plans.
</Info>
